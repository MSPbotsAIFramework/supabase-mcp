## Requirement understanding

One line: Connect Supabase to the Agent platform via MCP so Claude, ChatGPT, Cursor, or any MCP-compatible agent gets live, credentialed, logged access to a tenant's Supabase project (per the linked Conduit plugin page).

The ticket is a short Conduit/WYRE-style plug-in listing (`https://conduit.wyre.ai/plugins/supabase`), the same generic marketing-page template as the Box/Plaid/Figma/Neon/Sentry tickets in this batch (see the prior `[BLOCKED · vendor-mcp]` comment on this ticket, machine dev02, comment 1793382386721). It names a real, well-documented vendor (Supabase, an open-source Firebase alternative: Postgres database + Auth + Storage + Edge Functions + Realtime) and states two hard constraints that must survive into the implementation: credentials are encrypted (never persisted in the clear) and every action is logged. It does not name specific tools, specific endpoints, or specific user workflows — those are this design's job to fill in from Supabase's own Management API surface.

## Product design

### Goals / Non-goals

**Goals**: a first version of `supabase-mcp` that lets an agent, acting on behalf of one Supabase account (identified by the caller's own personal access token, forwarded per request), inspect and manage that account's Supabase **projects and their contents** through Supabase's public Management REST API:

- See what organizations and projects exist in the account.
- Run SQL — both a full read-write query and a read-only variant — against a project's Postgres database. This is Supabase's actual differentiator over a plain managed-Postgres vendor (the Management API exposes `POST /database/query` directly; unlike Neon, Supabase's control-plane API can run data-plane SQL, so "live access" naturally includes querying/mutating the data, not just the infrastructure around it).
- See, create, and delete preview database branches inside a project — Supabase's own branching feature, directly analogous to the `neon-mcp` design (PRD-21329).
- See, create (deploy), and update Edge Functions in a project — the other half of "live access" that database-only connectors (Neon) don't have: shipping server-side code.
- See and manage a project's secrets (environment variables consumed by Edge Functions) — this is where "credentials encrypted" in the ticket maps most directly onto a concrete capability.
- See a project's API keys, with the actual key value masked by default and revealed only on request.

**Non-goals** (v1):

- **Auth configuration** (SSO providers, JWT signing keys, third-party auth integrations) — these are tenant-identity-provider wiring, not "live access to the project's data/code", and misconfiguring them can lock out a project's real users. A separate ticket with its own threat model if ever needed.
- **Billing & compute** (addons, compute instance sizing, project upgrade/restore/pause), **network restrictions/bans, custom hostname, vanity subdomain, read replicas, disk/autoscale config, backups (physical/PITR) and restore points, database password rotation, JIT database access** — account/infrastructure administration, not what an AI agent doing day-to-day work on a Supabase project needs, and several are destructive/billing-affecting in ways that deserve a dedicated review.
- **Database migrations** (`apply`/`upsert`/`rollback` migration history) and **branch merge/push/reset/diff** — `supabase_run_sql` already covers ad-hoc schema and data changes; dedicated migration-history and branch-merge management is a bigger, separate capability (it mutates the project's migration ledger, not just its data) better scoped against a concrete need.
- **Storage bucket management, Realtime config, PostgREST config, custom TypeScript type generation, analytics/advisors, snippets, the OAuth app flow, and documentation search** — none were named by the ticket; several (advisors, docs search) are informational conveniences the community MCP offers but this org's connectors don't generally add without a specific requirement (see Decisions made by DEV01, item 1).
- Any UI. This is a backend MCP connector with no end-user-facing screen; "space with empty/loading/error states" does not apply.

### Acceptance criteria AC1..AC25

- **AC1**: Given a valid access-token header, When the caller asks what organizations exist, Then the connector returns the organization list (id, name) with no other input required.
- **AC2**: Given a valid access-token header, When the caller asks what projects exist, Then the connector returns the project list (ref, name, organization_id, region, status, created_at).
- **AC3**: Given a project ref, When the caller asks for that project's details, Then the connector returns the full project record Supabase reports for it.
- **AC4**: Given a project ref, When the caller asks for its API keys without asking to reveal them, Then the connector returns each key's name/type/id with the secret value masked (Supabase's own `reveal=false` default).
- **AC5**: Given a project ref, When the caller asks for its API keys and explicitly asks to reveal them, Then the connector passes `reveal=true` through and returns the full key values.
- **AC6**: Given a project ref and a SQL statement, When the caller calls the read-write SQL tool, Then the connector executes it against the project's database and returns the resulting rows.
- **AC7**: Given a project ref and an invalid SQL statement (e.g. a syntax error), When the caller calls the read-write SQL tool, Then the connector surfaces Supabase's rejection as a structured error, not a raw stack trace.
- **AC8**: Given a project ref and a SQL statement, When the caller calls the read-only SQL tool, Then the connector executes it as `supabase_read_only_user` and returns the resulting rows.
- **AC9**: Given a project ref and a mutating SQL statement (e.g. `insert`/`update`/`delete`/DDL), When the caller calls the read-only SQL tool, Then Supabase's own read-only role rejects it and the connector surfaces that rejection as a structured error (the connector does not attempt to parse or pre-judge the SQL itself).
- **AC10**: Given a project ref, When the caller asks what Edge Functions exist, Then the connector returns each function's slug/name/status/version/created_at/updated_at.
- **AC11**: Given a project ref and a function slug, When the caller asks for that function's details, Then the connector returns its full record (including the entrypoint path and import-map path if set).
- **AC12**: Given a project ref, a new function slug, source file(s), and an entrypoint path, When the caller asks to deploy it, Then the connector creates the function and returns the deployed record.
- **AC13**: Given a project ref and an **existing** function slug, When the caller asks to deploy with the same slug, Then the connector updates that function in place and returns the updated record (Supabase's deploy endpoint upserts by slug; the connector does not maintain its own create-vs-update branching logic).
- **AC14**: Given a project ref, When the caller asks what database branches exist, Then the connector returns each branch's id/name/parent_id/is_default/persistent/status.
- **AC15**: Given a project ref and a branch name, When the caller asks for that branch's details, Then the connector returns its full record.
- **AC16**: Given a project ref and a branch name, When the caller asks to create a new branch, Then the connector creates it and returns the new branch's record.
- **AC17**: Given a project ref and a branch, When the caller asks to delete it without explicitly confirming, Then the connector does **not** call Supabase's delete endpoint and instead tells the caller confirmation is required.
- **AC18**: Given a project ref and a branch, When the caller asks to delete it **with** explicit confirmation, Then the connector calls Supabase's delete endpoint and returns success.
- **AC19**: Given a project ref, When the caller asks what secrets are configured, Then the connector returns each secret's name, value, and updated_at exactly as Supabase returns them (Supabase's own API returns live values on this endpoint; see Non-functional → Security for how the connector avoids making that worse).
- **AC20**: Given a project ref and one or more name/value pairs, When the caller asks to create (or overwrite) secrets, Then the connector bulk-creates them and returns Supabase's confirmation; if a name starts with the reserved `SUPABASE_` prefix, Supabase's own validation rejects it and the connector surfaces that as a structured error.
- **AC21**: Given a project ref and one or more secret names, When the caller asks to delete them without explicitly confirming, Then the connector does **not** call Supabase's delete endpoint and instead tells the caller confirmation is required.
- **AC22**: Given a project ref and one or more secret names, When the caller asks to delete them **with** explicit confirmation, Then the connector calls Supabase's bulk-delete endpoint and returns success.
- **AC23**: Given no access-token header on the request, When any tool is called, Then the connector returns a structured 401 naming the required header, and no call reaches Supabase's API.
- **AC24**: Given an invalid, expired, or revoked personal access token, When any tool is called, Then the connector surfaces Supabase's 401/403 as a structured error (code + message), not a raw stack trace or an unhandled 5xx.
- **AC25 (multi-tenant isolation)**: Given two different access tokens used in two concurrent requests (two different Supabase accounts), When each request is handled, Then each one only ever sees/affects the Supabase account tied to its own header — the server holds no cross-request cache or shared state that could leak one account's data into another's response.

## Tech design

### Conclusion

Build `supabase-mcp` from scratch (main line A) against Supabase's public Management REST API (`https://api.supabase.com`, Bearer personal-access-token auth, no login/paywall — confirmed in this pass by fetching `https://api.supabase.com/api/v1-json` directly and cross-checking `https://supabase.com/docs/reference/api/introduction`). Follow the `hudu-mcp` / `neon-mcp` repo shape (same org, same stack) for module layout, credential middleware, structured error envelope, and response-size capping; adapt for Supabase's single fixed host (no per-tenant base-URL header needed, same reasoning as Neon) and for the one endpoint (`functions/deploy`) that takes a multipart/form-data body instead of JSON.

### Where the current implementation lives

Nowhere yet — `supabase-mcp@main` (a65bf17) is a two-line README with no source tree. There is no prior Supabase connector in `MSPbotsAIFramework` to extend.

### Option analysis

- **Build from Supabase's Management REST API directly (chosen)**: public, free, Bearer-token auth, documented resource model (organizations → projects → branches/functions/secrets/database), matches every other first-party connector in this org (HTTP wrapper over a vendor REST API, credentials from a request header). No sign-up gate, no partner/paid tier blocking any of the resources this design uses.
- **Wrap the community `supabase-community/supabase-mcp` server** — rejected per the vendor-mcp-development SOP: "open source / third-party MCP repos are reference only, always reimplement from scratch in `MSPbotsAIFramework`, never fork/mirror/directly modify". Used only as a sanity check on tool naming/category coverage, not as code; its OAuth-based login model doesn't fit this org's per-request-header credential contract anyway.
- **Expose the Postgres wire protocol directly (pgwire/psycopg) instead of Supabase's own HTTP query endpoint** — rejected: Supabase's Management API already offers `POST /database/query` (and a read-only variant) over the same HTTP/Bearer-token contract as every other tool in this connector; adding a second transport (raw Postgres wire protocol) for the same capability would be a materially different client/dependency/security surface for no documented requirement, unlike Neon where no such HTTP SQL endpoint exists at all.

### Data & API contract

**Transport**: Streamable HTTP, stateless, one container serving every tenant (SOP's three rules: credentials from headers only, per-request isolation, no server-side state).

**Credential header**:

| Header | Required | Meaning | How to get it |
|---|---|---|---|
| `X-Supabase-Access-Token` | Yes | Supabase personal access token, forwarded as `Authorization: Bearer <token>` to `api.supabase.com` | Supabase Dashboard → Account → Access Tokens (self-service, no partner/paid gate) |

No base-URL header: Supabase's Management API has exactly one host, unlike self-hosted vendors (Hudu) — same reasoning as the Neon and Figma designs.

**Upstream base URL**: `https://api.supabase.com` (confirmed via the fetched OpenAPI spec `https://api.supabase.com/api/v1-json` and `https://supabase.com/docs/reference/api/introduction`).

**Tool → endpoint map**:

| Tool | Method & path | Notes |
|---|---|---|
| `supabase_list_organizations` | `GET /v1/organizations` | |
| `supabase_list_projects` | `GET /v1/projects` | |
| `supabase_get_project` | `GET /v1/projects/{ref}` | |
| `supabase_get_project_api_keys` | `GET /v1/projects/{ref}/api-keys` | param `reveal` (bool, passthrough, defaults to `false` — see Decisions made by DEV01) |
| `supabase_run_sql` | `POST /v1/projects/{ref}/database/query` | body: `{query}`; success is `201`, not `200` |
| `supabase_run_readonly_sql` | `POST /v1/projects/{ref}/database/query/read-only` | body: `{query}`; executes as `supabase_read_only_user`; success is `201` |
| `supabase_list_functions` | `GET /v1/projects/{ref}/functions` | |
| `supabase_get_function` | `GET /v1/projects/{ref}/functions/{function_slug}` | |
| `supabase_deploy_function` | `POST /v1/projects/{ref}/functions/deploy` | **multipart/form-data**, not JSON: `file` part(s) (function source), `metadata` part (JSON: `entrypoint_path` required, optional `name`, `import_map_path`, `static_patterns`, `verify_jwt`); query param `slug` (new or existing — Supabase upserts by slug); success is `201` |
| `supabase_list_branches` | `GET /v1/projects/{ref}/branches` | |
| `supabase_get_branch` | `GET /v1/projects/{ref}/branches/{name}` | |
| `supabase_create_branch` | `POST /v1/projects/{ref}/branches` | body: `branch_name` required; optional `region`, `persistent`, `desired_instance_size`; success is `201` |
| `supabase_delete_branch` | `DELETE /v1/branches/{branch_id_or_ref}` | requires `confirm: true` argument (AC17/AC18); without it, the tool returns an error and never calls Supabase; note this is the top-level `/v1/branches/{id}` path, not under `/v1/projects/{ref}/...` |
| `supabase_list_secrets` | `GET /v1/projects/{ref}/secrets` | returns live secret values (`name`, `value`, `updated_at`) — this is the vendor's own response shape, not a connector choice; see Non-functional → Security |
| `supabase_create_secrets` | `POST /v1/projects/{ref}/secrets` | body: array of `{name, value}` (bulk, max 100 per call per the spec); names starting with `SUPABASE_` are rejected by Supabase; success is `201` |
| `supabase_delete_secrets` | `DELETE /v1/projects/{ref}/secrets` | body: array of secret names; requires `confirm: true` argument (AC21/AC22); success is `200` |

**Pagination**: none of the list endpoints used here (`organizations`, `projects`, `functions`, `branches`, `secrets`) are documented as cursor/offset-paginated in the fetched spec — they return the full array. `_json.dump_json_capped`'s response-size-driven truncation (reused from `hudu-mcp`/`neon-mcp`) still applies as a safety net for accounts with unusually large lists.

**Errors**: no single `FailureResponse`/`ErrorResponse` schema is reused consistently across the 115 paths in the fetched spec (checked: no such component schema exists). Design follows the `hudu-mcp`/`neon-mcp` defensive pattern — classify by HTTP status first (`_STATUS_TO_CODE`: 400/409/422 → `invalid_argument`, 401 → `unauthorized`, 403 → `forbidden`, 404 → `not_found`, **402 → `plan_limit`** (seen only on `functions/deploy` — Supabase's plan/quota gate, non-retryable), 429 → `rate_limited` retryable, 5xx/0 → `upstream_error` retryable), then best-effort extract a human message from the body (`error`/`message` keys if present, else the raw status line).

**Logging**: one line per upstream call — `method`, `path`, `status`, `ms`, `attempt` (no request/response bodies, no access token, no secret values) — same as `hudu-mcp`/`neon-mcp`'s `logger.info(...)` call. This satisfies the ticket's "every action logged" with the same meaning used by every other connector in this org (see Open question Q1), and is the specific control that keeps `supabase_list_secrets`'s live secret values (AC19) out of the connector's own logs even though Supabase's API itself returns them in plaintext.

### Key flow / sequence

Typical "inspect a project and ship a fix" flow:

1. Agent calls `supabase_list_projects` (or already has a `ref`).
2. Agent calls `supabase_run_readonly_sql(ref, query="select ... from information_schema.tables ...")` to understand the schema without any risk of mutating data.
3. Agent calls `supabase_run_sql(ref, query="update ... where ...")` to make the actual data fix, or `supabase_deploy_function(ref, slug, file, metadata)` to ship an Edge Function fix.
4. If the change is risky, the agent first calls `supabase_create_branch(ref, branch_name="agent-test")`, repeats steps 2–3 against the branch, then `supabase_delete_branch(ref, branch, confirm=true)` to tear it down once satisfied — mirroring the `neon_create_branch`/`neon_delete_branch` workflow in `neon-mcp`.
5. If the fix needs a new environment variable, agent calls `supabase_create_secrets(ref, [{name, value}])` before the next `supabase_deploy_function` call so the function can read it.

### Non-functional

- **Idempotency/concurrency**: every tool call builds its own `SupabaseCredentials`/`SupabaseClient` from the current request's header via a `contextvars.ContextVar` set by the middleware and reset in `finally` (copied from `hudu-mcp`/`neon-mcp`); the shared `httpx.AsyncClient` connection pool never holds credentials, so concurrent calls from different tenants cannot see each other's token. Writes (`run_sql`, `create_branch`/`delete_branch`, `deploy_function`, `create_secrets`/`delete_secrets`) are not retried on ambiguous failures (status `0` or `>=500`) — only GETs are retried, same rule as `hudu-mcp`/`neon-mcp`, so a write (including an arbitrary SQL statement) is never silently run twice.
- **Performance**: no SLA stated in the ticket; inherits the org-wide per-call budget (`_CALL_BUDGET_SECONDS = 100`, gateway tool-call timeout 120s) and the existing retry/backoff shape. `supabase_run_sql`/`supabase_run_readonly_sql` pass through whatever Supabase itself enforces as a statement timeout; the connector does not add its own SQL-level timeout beyond the shared HTTP call budget.
- **Security**: credential read only from `X-Supabase-Access-Token`, never persisted to disk/env/logs (SOP §3.1); 401 on missing header before any upstream call (SOP §3.2). `supabase_list_secrets` and `supabase_get_project_api_keys(reveal=true)` both return live, unmasked secret values from Supabase's own API — the connector's only control here is to never log or cache those response bodies (see Data & API contract → Logging); callers of these two tools should treat the response as sensitive the same way they would treat the Supabase Dashboard itself. `supabase_delete_branch` and `supabase_delete_secrets` both require `confirm: true` (AC17/AC18, AC21/AC22) as the two destructive tools in v1.
- **Multi-tenant isolation**: AC25; same guarantee `hudu-mcp`/`neon-mcp` document (per-request context var, no module-level credential state, cookie jar rejects all cookies so no session leaks across tenants sharing the process).
- **Observability**: one structured log line per upstream call (method/path/status/ms/attempt), no secrets — see Data & API contract → Logging.

## Decisions made by DEV01

(Also posted as a separate `[DESIGN DECISIONS]` ClickUp comment per `mcp-track.md` §2.4.)

1. **Scope is bounded to organizations/projects (read), SQL execution, Edge Functions, database branches, secrets, and API keys — not Auth config, Storage, Realtime, Billing, backups, migrations, read replicas, or any admin/billing surface.** Why: the ticket only says "live access" generically; the excluded categories are either account/billing administration an AI agent doing day-to-day project work would not need, or destructive/irreversible operations (project restore, backup restore, migration rollback) that deserve a dedicated review with their own threat model. This was checked directly against the fetched OpenAPI spec's path list (115 paths, all tags enumerated in this pass), not an automated summary — higher confidence than the equivalent note on the Neon design. Alternative not chosen: mirroring the community `supabase-mcp` server's full toolset (which also includes Docs search, Feedback, and an OAuth login flow) — rejected as unbounded scope for a v1 with no specific requirement driving the extra categories, and the OAuth model doesn't fit this org's per-request-header credential contract.
2. **Two SQL tools mirroring Supabase's own API split**: `supabase_run_sql` (full read-write, `POST /database/query`) and `supabase_run_readonly_sql` (`POST /database/query/read-only`, runs as `supabase_read_only_user`). Why: this is literally how the vendor's own REST API is shaped (two endpoints, not one endpoint with a flag); gives a safety-conscious caller a tool that cannot mutate data, enforced by Supabase's own read-only Postgres role rather than by this connector trying to parse or pre-judge SQL text (which is an unreliable thing to attempt and not this connector's job). Alternative not chosen: a single `run_sql(query, read_only: bool)` tool wrapping both — rejected because it would require the connector to pick which endpoint to call based on a caller-supplied flag it cannot verify, instead of exposing the vendor's own two safety tiers directly.
3. **`supabase_delete_branch` and `supabase_delete_secrets` both require an explicit `confirm: true` argument; no other tool (including `supabase_run_sql`, which can run DDL/DML) is gated.** Why: these two are the only operations in v1 that destroy something with no "undo" path through this connector (a deleted branch or a deleted secret value is simply gone); follows the exact `hudu-mcp`/`neon-mcp` precedent for a destructive-tool confirm gate. `supabase_run_sql` is intentionally not gated even though it can run arbitrary DDL/DML, because gating "the SQL tool" would contradict its entire purpose, and the vendor itself offers the safe alternative (`run_readonly_sql`) rather than a confirm flag on the write endpoint — gating it here would be inventing a safety mechanism Supabase's own API design doesn't have, for a capability (arbitrary SQL) that is the ticket's whole point.
4. **`supabase_get_project_api_keys` exposes Supabase's own `reveal` query parameter, defaulting to `false` (masked key values unless explicitly asked).** Why: project API keys (including the service-role key) are high-value secrets; defaulting to masked keeps them out of agent transcripts/logs by default while still letting a caller who needs the real value ask for it explicitly. Alternative not chosen: always passing `reveal=true` for a "complete" response — rejected as needlessly putting secret key values into every response and every downstream log/transcript that happens to capture it.
5. **`supabase_deploy_function` sends a multipart/form-data body (source file part + JSON metadata part), matching the vendor's own endpoint shape exactly.** Why: Supabase's `/functions/deploy` endpoint requires an uploaded source file (TypeScript/JavaScript), not an embeddable code string in a JSON body; `httpx` (already the connector's HTTP client per org convention) supports multipart uploads natively, so no new dependency is needed. Alternative not chosen: inventing a JSON-only wrapper that base64-encodes the source — rejected as diverging from the vendor's actual contract for no benefit.
6. **Credential header is a single `X-Supabase-Access-Token`; no base-URL header.** Why: Supabase's Management API has one fixed host (`api.supabase.com`), like Neon and unlike self-hosted vendors (Hudu); follows the SOP's `X-<Vendor>-<Credential>` naming convention and keeps the gateway's own auth header free of vendor credentials.
7. **Error handling classifies by HTTP status first, parses `error`/`message` best-effort second, same pattern as `hudu-mcp`/`neon-mcp`, with a dedicated `402 → plan_limit` entry.** Why: no single documented error-body schema is reused consistently across the 115 paths in the fetched OpenAPI spec; status-code classification does not depend on knowing the exact body shape. The `402` on `functions/deploy` specifically (seen nowhere else in the spec) gets its own non-retryable code rather than folding into generic `invalid_argument`, since "you've hit a plan/quota limit" is a materially different thing for a caller to act on than "your request was malformed".
